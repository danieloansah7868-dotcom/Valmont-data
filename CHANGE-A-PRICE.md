# Changing a price or a bundle

**You don't have to remember any of this — CI does.**
The `pages-in-sync` workflow regenerates the landing pages on every pull request and
fails with the exact command to run if the committed pages are stale. This file is
what that failure message points at.

> The workflow is committed at **`ci/seo.yml`** and needs one `git mv` to become
> active, because GitHub only runs workflows from `.github/workflows/` and the
> automation token that prepared this branch is not permitted to write there.
> Two commands, explained in **`ci/README.md`**.

---

## The four steps

### 1. Make the change in the places that must agree

| File | What it is | When |
| --- | --- | --- |
| `app/supabase/migrations/YYYY-MM-DD_<name>.sql` | The change for the **live** database — idempotent SQL you paste into the Supabase SQL editor. Copy the pattern in `2026-08-11_mtn_retail_lineup.sql` | always |
| `app/lib/demo-data.js` → `BUNDLES` | The mirror that the local mock DB, the demo seed **and the SEO generator** all read | always |
| `app/supabase/schema.sql` base seed | The base lineup itself | only when sizes are added or retired |

`lib/demo-data.js` is the one people forget, and it is the one the landing pages are
built from — which is exactly what the CI check catches.

### 2. Regenerate the pages

```bash
cd app && npm run seo:generate
```

Rewrites all 34 landing pages, the homepage price list and `<head>`, the FAQ schema
and size range, and `sitemap.xml`. Never hand-edit anything under `app/bundles/` —
those files are stamped *"generated by scripts/generate-seo-pages.js — do not edit"*.

### 3. Check

```bash
npm run seo:check                                     # pages vs the seed mirror
SEO_API=https://valmontdata.com npm run seo:check      # published pages vs the LIVE catalogue
npm run test:seo                                       # 96 SEO checks (add -- --base=http://localhost:8787 for live routes)
```

### 4. Commit everything

Generated HTML is committed on purpose (`.gitignore` does not exclude it), so:

```bash
git add -A && git commit -m "Catalogue: <what changed>"
```

## What CI does so you don't have to

| Job | When | What it does |
| --- | --- | --- |
| `pages-in-sync` (`ci/seo.yml`) | every PR and push to `main` | Regenerates the pages (with the committed date pinned, so only real content changes show up) and **fails the build** if they differ from what is committed. Also runs the 96-check SEO suite. |
| `production-audit` | Mondays 06:17 UTC, or *Run workflow* in the Actions tab | Compares the pages **published on valmontdata.com** with the **live catalogue** at `/api/bundles`, and opens an issue if they disagree. |

That second job is the important one: it catches a price changed **directly in the
Supabase SQL editor** with no git commit — the one kind of drift no other check can
see, because it is the drift between what Google was told and what checkout charges.

## What updates itself, and what doesn't

**Derived from the catalogue — never hand-write these:** prices, bundle counts, size
ranges, per-GB figures, "from GH₵…" in titles and descriptions, the homepage price
table, `sitemap.xml` URLs and `lastmod`, the FAQ size-range sentence, and the
`FAQPage` schema on `faq.html` and `store.html` (both are read back out of the
visible page).

**Hand-written — edit the file directly:** the prose in `about.html`,
`contact.html`, `store.html`, `faq.html` answers, and the page copy templates inside
`scripts/generate-seo-pages.js`. The generator only ever touches the regions between
its `<!--SEO:…:START/END-->` markers; if you delete a marker it throws instead of
guessing.

**Vocabulary** (`app/lib/keywords.js`) is the third kind: add a synonym there and it
appears in the `keywords` meta, the visible "Also searched as:" rows, on-site search,
the ValmontAI assistant and the WhatsApp bot at once — then `npm run seo:generate`.
